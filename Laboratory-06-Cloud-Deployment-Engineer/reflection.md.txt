# Mission Reflection

## 1. How does writing a `docker-compose.yml` file make a cloud engineer's job easier compared to manually typing commands?

Writing a `docker-compose.yml` file transforms deployment from a long string
of memorized commands into a **declarative document**. Instead of remembering
the correct flags, environment variables, ports, and network links for each
container, I simply describe *what I want* and Docker Compose figures out
how to build it. The file can be reviewed, version-controlled, and
reproduced by any teammate in seconds. If I make a mistake, I fix one line
in the file instead of retyping an entire command. It also eliminates
"it worked on my machine" problems, because the YAML file itself is the
single source of truth for the deployment.

## 2. What happens if you make an indentation error (like using a Tab instead of Spaces) in a YAML file?

YAML is **strictly whitespace-sensitive** — indentation defines the
structure and hierarchy of the data. If I accidentally use a Tab instead
of Spaces, Docker Compose will throw a parsing error and refuse to start
any services. The error message usually points to a line number, but it
can be confusing because the tab character is invisible in most editors.
This is why the standard is to use **two spaces per indentation level**
and configure the editor to insert spaces when Tab is pressed.

## 3. Why did we use environment variables (like `MYSQL_PASSWORD`) in the Compose file?

Environment variables keep configuration **separate from code**. Putting
passwords, database names, and usernames directly into the image or into
a hardcoded command would be insecure and inflexible. By using environment
variables, I can:

- Change values without rebuilding the image.
- Keep secrets out of version control (by using a `.env` file).
- Reuse the same Compose file across development, staging, and production.

It is a best practice borrowed from the Twelve-Factor App methodology.

## 4. How did it feel to deploy a fully functional enterprise cloud storage system (Nextcloud) in just a few minutes?

Honestly, it felt **empowering**. In previous missions, deploying a single
container already required several steps and careful typing. Watching
Nextcloud — the same kind of software that powers real companies — spin up
alongside its own database with a single `docker-compose up -d` command
made me realize how much power Infrastructure as Code gives to a cloud
engineer. In just a few minutes I had replicated what would traditionally
take hours of manual configuration, and I could tear it all down with one
short command.

## 5. How has your understanding of Cloud Computing evolved since Mission 1?

In Mission 1, I thought cloud computing was mostly about **storing files
somewhere on the internet**. Now I understand it as a **discipline of
declarative infrastructure** — where servers, networks, and services are
described in code, versioned, and deployed reproducibly. I have moved from
a user's mindset ("where do I upload my files?") to an engineer's mindset
("how do I design, deploy, and tear down this system reliably?"). Docker
Compose is the bridge between those two worlds, and this mission made that
shift feel concrete for me.
